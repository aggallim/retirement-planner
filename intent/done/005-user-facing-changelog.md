# 005 — User-facing changelog, built into the app

## Status

Proposed. Drafted and then substantially revised through direct
conversation with the user — see "Revision note" and "Decisions confirmed
with the user" below. Nothing here is an assumed default.

## Revision note

An earlier version of this intent proposed GitHub Releases as the delivery
mechanism (tag = the `sw.js` cache version, release notes = plain-language
entries). The user reconsidered: this app is deliberately self-contained
and offline-capable (`CLAUDE.md` — no backend, nothing leaves the device,
works offline via the service worker), and a GitHub Release lives entirely
outside that boundary — it needs GitHub and a network connection to view,
neither of which the app itself ever requires. Building the user-facing
changelog *into* the app instead keeps the whole feature inside the PWA,
consistent with everything else about it. This also happens to remove a
real constraint the Releases version had: publishing a Release necessarily
had to happen *after* a PR merged (a tag needs a commit on `main` to point
at), whereas an in-app changelog entry is just part of `index.html` and can
land inside the PR itself, at the same point as the existing
`CHANGELOG.md` entry.

## Problem

`CHANGELOG.md` (added in intent 001) is explicitly developer-facing — its
own header says so, and its entries mix real feature/bug content with
implementation detail: field names, function names (`migratePerson()`,
`schemaVersion`), CSS class names, doc section numbers, and a line
referencing the intent/spec file. Someone actually using the app has no
equivalent surface — no plain-language "what's new" reachable from inside
the app itself.

## Outcome

1. **A "What's new" view inside the existing ⚙ Data menu** (the
   `SettingsMenu` component built for intent 004's Export/Import). Not a
   new header control — the header was just decluttered for mobile
   (intent 003), and reusing the existing menu avoids re-crowding it.
2. **Inclusion rule, specified directly by the user, not inferred:** a
   change gets an entry if and only if it changes something a user of the
   running app would experience — a new or changed feature, a calculation
   or behaviour change, a bug fix, a UI change. A change that doesn't touch
   what the user sees or experiences does not — repo/process files
   (`CLAUDE.md`, `CONTRIBUTING.md`), CI workflow changes, the test harness,
   internal refactors with no behaviour change, and edits to
   `docs/TOOL_DOCUMENTATION.md` itself are all out of scope even though
   they're real merges to `main`. (001, the engine test harness, is the
   existing worked example of a merge that would not get an entry.)
3. **The version label reuses the `sw.js` `CACHE` number** (`v3`, `v4`,
   `v5`, …) — no new versioning scheme. Not every cache-version bump gets
   an entry (see point 2), so the sequence shown to the user has gaps
   (`v2`, the engine test harness, never appears) — that's fine, a gap
   communicates nothing false.
4. **Entries are plain language, feature/fix-oriented bullets** — no file
   names, function names, CSS classes, doc section numbers, or intent/spec
   references. Written by whichever Claude session implements the
   requirement, as part of the same PR that changes `index.html` — not a
   separate manual pass, not content generated by inferring intent from a
   diff. The editorial judgment (is this user-facing, and what does it
   mean in plain language) stays with the implementing agent, which
   already has full context on what it just built.
5. **A static, always-available full history, newest first** — no
   "unseen update" badge or indicator, no tracking of what the user has or
   hasn't already seen. Opening the "What's new" view always shows
   everything, in the same shape `CHANGELOG.md` already uses.
6. **Backfill v3, v4 and v5** (002, 003, 004) as a one-time task in the
   same PR that introduces this feature, translating their existing
   `CHANGELOG.md` entries into plain language. **v2 (001) and the initial
   deploy (v1) do not get backfilled** — v2 because it's internal-only (the
   worked example in point 2), v1 because it's outside what the user asked
   to backfill.

## Non-goals

- **No GitHub Releases, no git tags for this purpose.** Superseded by the
  in-app approach — see Revision note. `CHANGELOG.md` remains the only
  place tags/requirement numbers are cross-referenced.
- **No semantic versioning.** The version label is the existing
  cache-version number, not a `major.minor.patch` scheme — there's no API
  or external consumer for that to mean anything to.
- **No "unseen" tracking or badge.** Explicitly decided against — see
  Outcome point 5. No new `localStorage` key for a last-seen version.
- **No CI-automated editorial judgment.** The implementing agent decides
  what's user-facing and writes the entry directly; there is no automation
  step at all in this version (unlike the Releases version, which at least
  needed a mechanical publish step).
- **No change to `CHANGELOG.md`'s existing audience or content.** This is
  an additive, in-app surface, not a replacement.
- **No entry for every merge.** Only merges with user-visible content —
  see the inclusion rule.
- **No ongoing backfill process.** The v3–v5 backfill is a one-time
  catch-up, not a pattern applied retroactively again later.

## Constraints

- **Single source of truth, inline in `index.html`.** The changelog
  entries live as a plain JS array/constant (module level, alongside
  `PERSISTED_FIELDS` and friends in the Persistence section) — consistent
  with the single-file PWA constraint (`CLAUDE.md`, tool docs §5.5). No
  separate JSON/markdown file fetched at runtime, which would need its own
  service-worker cache entry to keep working offline.
- **Respect the module-level/memoised component pattern** (`CLAUDE.md`,
  tool docs §5.3). Whatever UI shows the "What's new" list — a new
  sub-view within `SettingsMenu`, or a small new module-level component it
  renders — must not reintroduce an inline subcomponent definition; that's
  the exact bug class that made the sliders unusable once already.
- **No new dependencies.** Plain React state for any view-toggling inside
  the existing menu; no new library.
- **Not an engine change.** `projectJoint()` is untouched; no new
  `tests/test-engine.js` cases expected.
- **Exact placement within the `SettingsMenu` popover is a spec-stage
  decision, not settled here** — e.g. a third section alongside
  Export/Import in the same panel, vs. a "What's new" trigger that swaps
  the panel to a secondary view with its own back action. The concern to
  resolve at spec stage: five-plus backfilled entries plus future growth
  could make a single non-scrolling panel unwieldy next to the existing
  Export/Import controls.
- **Update `docs/TOOL_DOCUMENTATION.md` in the same PR:** a new §3
  subsection documenting the "What's new" view; a new §8 Build history
  entry.
- **Add a `CHANGELOG.md` entry** naming this intent, per `CLAUDE.md` — the
  developer-facing file is unaffected in role, but this requirement is
  itself a merge to `main` and needs its own technical entry same as any
  other.
- **Backfilling v3–v5 needs the exact version-to-requirement mapping**:
  v3 = 002 (extra savings accounts), v4 = 003 (mobile sticky summary bar),
  v5 = 004 (JSON import/export) — already established via `git log
  --reverse -- sw.js` and `git show <commit>:sw.js` while drafting the
  earlier version of this intent.
- **`CLAUDE.md`/`CONTRIBUTING.md` need updating** to document this as a
  new, conditional same-PR step (add a `USER_CHANGELOG` entry in
  `index.html`, worded "if user-facing," alongside the existing
  unconditional `CHANGELOG.md`-entry and docs-update requirements) —
  replacing the never-implemented GitHub-Release step the earlier version
  of this intent would have added.
- **Bump the service worker cache version** (`sw.js`) as with any
  `index.html` change — this includes the backfill PR itself.

## Decisions confirmed with the user

This intent was drafted, then substantially revised, through direct
conversation — nothing here is an assumed default.

**First round** (delivery mechanism, before the revision):
- User specified the inclusion rule directly, in their own words (quoted
  below), rather than having it inferred.
- User confirmed GitHub Releases as the delivery mechanism, with a
  specific rationale (converges "user-friendly surface" and "does this add
  complexity" into one, reusing the cache version as the tag).
- User confirmed backfilling v3–v5 (002–004), excluding v2/v1.

**Second round** (the revision, superseding the delivery-mechanism
decision above): user rejected GitHub Releases specifically to avoid an
external dependency, and asked for an in-app "friendly version" instead,
reusing the same versioning. Four further forks were then resolved
explicitly:
1. **Version identity** — reuse the `sw.js` cache number (`v3`, `v4`,
   `v5`, …), gaps and all, over inventing a separate user-facing-only
   counter or dropping numbers for dates.
2. **Placement** — inside the existing ⚙ Data menu, not a new dedicated
   header control, specifically to avoid re-crowding the header after
   intent 003's mobile decluttering work.
3. **Unseen indicator** — none. A static, always-available list, no
   last-seen tracking.
4. **History depth** — full history, newest first, same shape as
   `CHANGELOG.md`.

The inclusion rule, unchanged by the revision, in the user's own words:

> "if something changes that the consumer sees then it should be included
> in the app changelog. if something changes on main which doesn't change
> anything that impacts a user using the app then it doesn't need a
> changelog update. For example if you change something in claude.md, that
> doesn't impact the app so no changelog additions needed. But if you
> change a calculation in the app, that affects the user so should be
> tracked."
