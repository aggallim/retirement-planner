# 005 — User-facing changelog via GitHub Releases

## Status

Proposed. Drafted through direct conversation with the user rather than
shipped on assumed defaults — see "Decisions confirmed with the user" below.

## Problem

`CHANGELOG.md` (added in intent 001) is explicitly developer-facing — its
own header says so, and its entries mix real feature/bug content with
implementation detail: field names, function names (`migratePerson()`,
`schemaVersion`), CSS class names, doc section numbers, and a line
referencing the intent/spec file. Someone actually using the app has no
equivalent surface — no dated, plain-language "what's new," and no way to
be notified when something changes.

## Outcome

1. **GitHub Releases become the user-facing changelog.** Not a new file —
   `CHANGELOG.md` keeps its existing technical/developer role unchanged.
2. **Inclusion rule, specified directly by the user, not inferred:** a
   change gets a Release if and only if it changes something a user of the
   running app would experience — a new or changed feature, a calculation
   or behaviour change, a bug fix, a UI change. A change that doesn't touch
   what the user sees or experiences does not — repo/process files
   (`CLAUDE.md`, `CONTRIBUTING.md`), CI workflow changes, the test harness,
   internal refactors with no behaviour change, and edits to
   `docs/TOOL_DOCUMENTATION.md` itself are all out of scope for a Release
   even though they're real merges to `main`. (001, the engine test
   harness, is the existing worked example of a merge that would not have
   gotten one.)
3. **Release tag = the `sw.js` `CACHE` version at that merge** (`v3`, `v4`,
   `v5`, …) — reusing the version signal that already exists rather than
   inventing semver or any other new scheme. Not every cache-version bump
   gets a Release (see point 2) — the tag sequence has gaps where a merge
   was internal-only, and that's fine; a gap communicates nothing false.
4. **Release notes are plain language, feature/fix-oriented bullets** —
   no file names, function names, CSS classes, doc section numbers, or
   intent/spec references. Composed by whichever Claude session implements
   the requirement, as one more PR-closeout action alongside the existing
   `CHANGELOG.md` entry and docs update — not a separate manual curation
   pass by the user, and not content generated by a CI script guessing at
   intent from a diff. The editorial judgment (is this user-facing, and
   what does it mean in plain language) stays with the implementing agent,
   which already has full context on what it just built.
5. **Backfill 002, 003 and 004** (tags `v3`, `v4`, `v5`) as a one-time task
   in the same PR that introduces this workflow, translating their existing
   `CHANGELOG.md` entries into plain language. **001 (`v2`) and the initial
   deploy (`v1`) do not get backfilled** — 001 because it's internal-only
   (the worked example in point 2), the initial deploy because it's outside
   what the user asked to backfill.

## Non-goals

- **No semantic versioning.** The tag is the existing cache-version number,
  not a `major.minor.patch` scheme communicating compatibility or
  breaking-change semantics — there's no API or external consumer here for
  that to mean anything to.
- **No CI-automated editorial judgment.** Automation, if any is used for
  the mechanical publish step (see Constraints), only publishes content the
  implementing agent already decided on and wrote — it does not decide
  *whether* a change is user-facing or generate the notes' wording itself.
- **No change to `CHANGELOG.md`'s existing audience or content.** This is
  an additive surface, not a replacement or a rewrite of that file.
- **No Release for every merge.** Only merges with user-visible content get
  one — see the inclusion rule.
- **No ongoing backfill process.** The 002–004 backfill is a one-time
  catch-up, not a pattern applied retroactively again later.

## Constraints

- **No MCP tool in this environment creates a GitHub Release directly.**
  The GitHub MCP server here exposes `list_releases`, `get_latest_release`
  and `get_release_by_tag` — read-only. The actual publishing mechanism
  (candidate: an annotated git tag carrying the plain-language notes as its
  tag message, pushed by the implementing session, plus a new
  `.github/workflows/release.yml` triggered on tag push that runs
  something like `gh release create "$GITHUB_REF_NAME" --notes-from-tag`)
  is a spec-stage decision, not settled here.
- **Default `GITHUB_TOKEN` permissions for release creation must be
  verified empirically, not assumed.** This repo has already hit two
  surprises where the default Actions token had less permission than
  expected — GitHub Pages needed a one-time manual Settings change
  (`intent/done/001` era), and branch deletion still isn't possible from
  this environment's git proxy at all. `contents: write` is documented as
  sufficient for release creation and should work, but the spec/plan stage
  must actually test that against this repo rather than assume it.
- **This is necessarily a post-merge action**, unlike the `CHANGELOG.md`
  entry (which lands inside the PR, pre-merge): a Release/tag has to point
  at a commit that exists on `main`, so it can only be created after the
  PR merges. `CLAUDE.md`/`CONTRIBUTING.md`'s existing lifecycle step 8
  ("Merge, then delete the branch") gains a conditional follow-on: create
  the GitHub Release, but only if the change was user-facing.
- **Backfilling 002–004 needs the exact tag-to-commit mapping already
  established** (see the table above the "Outcome" section in this
  intent's originating conversation, or re-derive via `git log --reverse
  -- sw.js` and `git show <commit>:sw.js`) — each Release should point at
  the merge commit where that requirement's `CACHE` version first took
  that value, not at the current tip of `main`.
- **`CLAUDE.md` and `CONTRIBUTING.md` need updating** to document this as a
  new, conditional PR-closeout step — worded as "if user-facing," unlike
  the unconditional `CHANGELOG.md`-entry and docs-update requirements.

## Decisions confirmed with the user

This intent was drafted through direct conversation, not shipped on
assumed defaults. Two explicit forks were raised and resolved:

1. **Delivery mechanism** (GitHub Releases vs. a plain file such as
   `docs/WHATS_NEW.md`) — user confirmed **GitHub Releases**, specifically
   because it converges two needs (a user-friendly surface, and answering
   "does GitHub Releases help or just add complexity") into one: reusing
   the existing cache-version number as the tag means no new versioning
   scheme, and Releases give a rendered, dated, watchable page for free
   where a plain file would not.
2. **Backfill scope** — user confirmed **backfilling 002, 003 and 004**,
   explicitly excluding 001 (matching the user's own worked example of a
   non-user-facing change) and the initial deploy (outside what was asked).

The inclusion rule in Outcome point 2 was specified directly by the user in
their own words, not inferred by Claude:

> "if something changes that the consumer sees then it should be included
> in the app changelog. if something changes on main which doesn't change
> anything that impacts a user using the app then it doesn't need a
> changelog update. For example if you change something in claude.md, that
> doesn't impact the app so no changelog additions needed. But if you
> change a calculation in the app, that affects the user so should be
> tracked."
